# ADR 0005: HMAC-chained audit log with periodic anchoring

Maintainer: Platform Engineering + Security Engineering (`#sentinelx-secops`)
Last reviewed: 2026-05-30

- Status: Accepted
- Date: 2026-05-30
- Deciders: Founding engineering team, CISO
- Supersedes: None
- Superseded by: None

## Context

The audit log is the platform's most load-bearing artifact. It is the
evidence we hand to auditors, the forensic record we hand to incident
responders, and the integrity claim we make to customers. If the
audit log can be tampered with — or even appears to be tamperable —
the product loses its primary trust property.

Requirements:

- **Tamper evidence**: any modification, insertion, or deletion is
  detectable.
- **Append-only**: the log is functionally write-only.
- **Verifiable offline**: an auditor with a copy of the log and the
  appropriate keys can verify integrity without the platform.
- **High write throughput**: peak around 5,000 entries/second per
  cluster.
- **Reasonable read latency**: queries by tenant, actor, target, time
  range must return in < 500 ms p99.
- **Operational simplicity**: incident responders should not need a
  cryptographer on call to verify a chain.
- **Forward path to a stronger primitive** if compliance or threat
  model demands it (KMS-backed signatures, transparency-log anchoring).

Threat model:

- The adversary may have **read** access to the Postgres replica.
  Cannot deny that.
- The adversary may have **temporary write** access (compromised app
  credential or DBA). We need to detect tampering after the fact.
- The adversary may have **persistent root** on a single pod. We need
  to detect that they cannot retroactively backfill chain entries
  without alarming the verifier.
- The adversary may try to **truncate** the log. We need to detect
  truncation.

## Decision

We will implement an **HMAC chain** in Postgres, with **periodic
external anchoring** to S3 (Object Lock + Versioning) and to a
customer-visible attestation endpoint.

### Chain structure

Each audit row carries a `chain_hash` that depends on the row's
content and the previous row's `chain_hash`:

```
chain_hash[i] = HMAC-SHA256(
    key   = chain_key[tenant_id, epoch],
    data  = canonical_bytes(row[i]) || chain_hash[i-1]
)
```

where `canonical_bytes(row[i])` is a deterministic byte encoding of
the row payload (we use canonical CBOR via `ciborium`).

The first row of a chain (`row[0]`) uses a fixed genesis seed for
`chain_hash[-1]`:

```
chain_hash[-1] = SHA256("sentinelx:audit:genesis:" || tenant_id || ":" || epoch_id)
```

`tenant_id` partitions chains so a noisy tenant cannot block a quiet
tenant. `epoch_id` advances every time the chain key rotates (every
90 days, or on demand).

### Key management

- **Chain key** is per-tenant-per-epoch, 256-bit, generated by the
  platform.
- Stored encrypted with the **platform master key** (held in the
  secret manager — AWS Secrets Manager, GCP Secret Manager, Vault).
- The chain key is loaded into memory at boot, never written to logs,
  zeroed on shutdown.
- Rotation: a new epoch begins; the genesis row of the new epoch
  carries `prev_epoch_anchor = HMAC(old_key, old_chain_head)` so the
  two chains are cryptographically linked.

### Periodic anchoring

Every 5 minutes the chain rotator:

1. Reads the latest `chain_hash` for each `(tenant, epoch)` pair.
2. Writes a small **anchor manifest** (JSON) to S3 with Object Lock
   (Compliance mode, 7-year retention) containing:
   - `tenant_id`
   - `epoch_id`
   - `chain_head_hash`
   - `last_row_id`
   - `wallclock_utc`
   - `manifest_signature` — HMAC of the manifest with the **anchor
     key** (separate from the chain key, also 256-bit).
3. Records the anchor in `audit.anchor` (Postgres) for fast lookup.

Anchors are tamper-evident in their own right: they are
write-once-read-many in S3 with Object Lock. An auditor with
access to the S3 bucket can verify that the chain head at time T was
what we claimed at time T+5min.

The 5-minute window is the **maximum tamper window** in which a
sophisticated adversary could rewrite the chain without producing a
detectable anchor mismatch. We considered 1 minute and 15 minutes;
5 minutes is the chosen tradeoff between forensic granularity and S3
PUT cost.

### Public attestation endpoint

`GET /v1/audit/attestation?tenant=acme&epoch=N` returns the most
recent anchor manifest for the tenant, signed by the anchor key.
Customers and auditors can pull this on a schedule and store it
externally.

### Verification

The CLI `sx audit verify` accepts:

- A Postgres connection string (or a Postgres dump).
- The chain key for the relevant epoch (extracted by an authorized
  operator from the secret manager).
- An anchor manifest (or the bucket name + tenant + epoch).

It walks every row in `(tenant, epoch)`, recomputes the chain hash,
and checks:

1. Every chain hash matches.
2. The final chain head matches the anchor manifest's claimed head.
3. The anchor manifest's signature is valid.
4. No row is missing (gaps in the per-tenant monotonic counter are
   flagged).

A clean run prints `chain OK: N entries, head = ...`. Any mismatch
prints the index of the first divergence.

### Storage layout

```sql
CREATE TABLE audit.entry (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    epoch_id        INTEGER NOT NULL,
    seq             BIGINT NOT NULL,        -- per (tenant, epoch) counter
    occurred_at     TIMESTAMPTZ NOT NULL,
    actor           JSONB NOT NULL,
    action          TEXT NOT NULL,
    target          JSONB NOT NULL,
    payload         BYTEA NOT NULL,         -- canonical CBOR
    chain_hash      BYTEA NOT NULL,         -- HMAC-SHA256 = 32 bytes
    UNIQUE (tenant_id, epoch_id, seq)
);

CREATE TABLE audit.anchor (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    epoch_id        INTEGER NOT NULL,
    chain_head_hash BYTEA NOT NULL,
    last_seq        BIGINT NOT NULL,
    wallclock_utc   TIMESTAMPTZ NOT NULL,
    s3_object_key   TEXT NOT NULL,
    s3_version_id   TEXT NOT NULL
);
```

Writes go through `crates/sx-audit/src/chain.rs::append`, which:

1. Begins a serializable PG transaction scoped to the (tenant, epoch)
   sequence counter (via `SELECT ... FOR UPDATE` on the
   sequence-anchor row).
2. Reads the current `chain_hash`.
3. Computes the new row's `chain_hash`.
4. Inserts the row.
5. Commits.

The `FOR UPDATE` serializes writes per (tenant, epoch), which gives
us the per-tenant throughput cap of around 2,000 entries/second
(measured). For tenants near the cap we shard by adding
`shard_id` -> per `(tenant_id, epoch_id, shard_id)` chains; the
verifier walks each shard independently and the anchor manifest lists
all shard heads.

## Consequences

### Positive

- **Operationally simple.** HMAC-SHA256 is a single primitive
  understood by every reviewer. The verifier is a 200-line Rust
  function.
- **Cheap.** Compared to a Merkle tree, every append is O(1) hash
  operations rather than O(log N). No tree rebalancing.
- **Verifiable offline.** With the chain key and a Postgres dump, an
  auditor can re-walk the chain on their laptop.
- **Anchor-based external tamper evidence.** Even with full Postgres
  write access, an adversary cannot rewrite history without leaving
  a mismatch with the S3 Object Lock anchor.
- **Per-tenant isolation.** A loud tenant does not slow a quiet
  tenant; per-tenant chains can be rotated independently.

### Negative

- **HMAC is symmetric.** The chain key is required to verify. If we
  want a customer to verify independently of us, they need the key
  (which we will not give) or a public-key signature path. The
  anchor manifest's signature covers most of this need at the
  manifest level, but row-by-row verification requires the chain key.
- **5-minute tamper window.** A motivated adversary with PG write
  access could rewrite the most recent 5 minutes of audit log
  without an external anchor catching it. The window is bounded but
  not zero.
- **Per-tenant per-epoch throughput cap.** ~2,000 writes/sec is fine
  today but a single noisy tenant could saturate. We shard above
  that threshold.

### Risk register

| Risk                                                       | Mitigation                                                              |
| ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| Chain key leaks; attacker can forge undetectable entries.  | 90-day rotation; new epoch invalidates forgeries beyond the rotation.   |
| Anchor key leaks; attacker can forge anchor manifests.     | Anchor key stored separately; rotated independently every 90 days.      |
| S3 Object Lock misconfigured; anchors are deletable.       | CIS-benchmarked Terraform; weekly compliance scan asserts Object Lock.  |
| Verifier in the CLI has a bug; missed tampering.           | Verifier test suite includes 200 fuzz cases; differential test vs spec. |
| Postgres write skipped during outage; chain has a gap.     | Per-(tenant, epoch) seq monotonicity check during verify.               |
| Adversary deletes the latest anchor manifest.              | S3 Object Lock + Versioning + cross-account replication.                |

## Future migration to KMS-backed signatures

We expect to migrate to a KMS-backed signature scheme when any of:

- A customer demands cryptographic non-repudiation that does not
  trust us (we hold the symmetric key).
- A compliance framework (SOC2, ISO27001) auditor objects to the
  symmetric-key model.
- We need a transparency-log style proof we can publish.

The likely target:

- **KMS-managed signing key** (asymmetric, EdDSA via Ed25519 or
  ECDSA P-256), with the **public key** published as a customer-
  visible artifact.
- Each row stores `signature = KMS.sign(canonical_bytes(row) ||
  prev_chain_hash)` in addition to or in place of the HMAC.
- Verification becomes public: anyone with the public key and the
  Postgres dump can verify.
- Throughput drops because KMS calls are expensive (~10 ms each).
  We mitigate by **batching**: sign a manifest of N rows every N
  rows or T milliseconds, whichever first.

The migration plan keeps the HMAC chain in place for backward
compatibility and adds the KMS signature as a parallel field. The
verifier prefers the signature when present and falls back to the
HMAC. After 90 days we drop the HMAC from new rows.

## Alternatives considered

### Alternative 1: Merkle tree of audit entries

Standard transparency-log primitive (Certificate Transparency,
SigStore Rekor).

**Why not (yet):**

- Higher operational complexity: tree maintenance, balanced
  insertion, periodic root signing.
- The benefit of a Merkle tree over a chain is **inclusion proofs**
  for individual entries — useful when you want to prove that one
  entry is in the tree without revealing the tree. For a private
  audit log served to authenticated callers, that property is not
  worth the complexity.
- Existing Rust ecosystem support for transparency logs (Rekor) is
  good but heavier than our use case warrants.
- We will revisit if we ever publish the log to the public.

### Alternative 2: Write-once external append-only log (Kafka, AWS QLDB)

Push every audit entry to an external append-only system.

**Why not:**

- Adds an SPOF for our most load-bearing artifact.
- AWS QLDB is being deprecated by AWS.
- Kafka topics are append-only but not tamper-evident on their own;
  we would still need a hash chain on top.
- BYOC customers may not allow us to use a managed AWS service.

### Alternative 3: HSM-backed signing per entry from day one

Sign every entry with a hardware-backed key.

**Why not (yet):**

- Per-entry HSM calls cap throughput around 100/sec; we need ~5k/sec.
- Batched HSM signing is what the KMS migration does — same idea,
  later, when the compliance need is real.

### Alternative 4: Blockchain anchoring (public chain)

Anchor the chain head to a public blockchain (Bitcoin, Ethereum).

**Why not:**

- Cost and tooling drift.
- Forces customers to trust a third party (the chain operator).
- Privacy is awkward: chain heads are hashes but the cadence and
  volume leak information.
- S3 Object Lock gives us most of the durability properties without
  the public-chain overhead. We accept "we operate the bucket" as
  trust assumption — the anchor key is independent of the chain key
  precisely so a single-key compromise does not falsify both.
