# ADR 0003: JWT HS256 internally, pluggable OIDC for federation

Maintainer: Platform Engineering (`#sentinelx-platform`)
Last reviewed: 2026-05-30

- Status: Accepted
- Date: 2026-05-30
- Deciders: Platform engineering, Security engineering
- Supersedes: None
- Superseded by: None

## Context

SentinelX has three distinct auth-bearing flows:

1. **Interactive users** signing in to the dashboard with email +
   password, optionally via their corporate IdP.
2. **Programmatic clients** — CI scripts, the operator CLI, the remote
   agent — calling the HTTP surface with a long-lived token (or a
   short-lived token derived from a long-lived secret).
3. **Service-to-service** within the monolith: nothing crosses the
   network, so no transport-level auth is needed, but action-level
   authorization still applies.

The platform must support:

- **Self-serve signup** (email + password), at least for the trial /
  managed offering.
- **Enterprise SSO** via SAML or OIDC, with at least Okta, Azure AD
  Entra, and Google Workspace working day-one.
- **Per-tenant federation policy**: tenant A enforces OIDC-only;
  tenant B allows password fallback.
- **Refresh token rotation** with a stolen-refresh-token detection
  mechanism.
- **A short token lifetime on the access path** so revocation latency
  is small.

Threat model headlines:

- Stolen access token: limited blast radius if TTL is short (we set 15
  minutes).
- Stolen refresh token: must be detectable by reuse; rotation enforces
  this.
- Stolen signing key (the most damaging): we need a clear migration
  path and rotation runbook.
- Compromised IdP: we cannot prevent it; we can scope blast radius
  with sane defaults (no JIT admin assignment).

## Decision

The decision has two halves: how we sign tokens, and how we accept
federated tokens.

### Half 1: Internal tokens are JWT signed with HS256

Tokens minted by SentinelX (access tokens and refresh tokens) are
**JWT signed with HS256** using a per-environment shared secret stored
in the secret manager (AWS Secrets Manager, GCP Secret Manager, or
HashiCorp Vault depending on deployment).

- **Algorithm**: HS256 (HMAC with SHA-256).
- **Secret**: 256-bit random, generated by the deploy pipeline,
  rotated every 90 days with a 14-day overlap window.
- **Issuer**: `https://api.sentinelx.io/` (or the customer-specific
  issuer for BYOC).
- **Access token TTL**: 15 minutes.
- **Refresh token TTL**: 30 days, rotated on every use.
- **Refresh token storage**: hashed (SHA-256) in Postgres with a
  `replaced_by` column for reuse detection.

The access token payload is intentionally small:

```json
{
  "iss": "https://api.sentinelx.io/",
  "sub": "user_01HXYZ...",
  "aud": "sentinelx-api",
  "exp": 1764800000,
  "iat": 1764799100,
  "tenant": "acme",
  "scope": "engagement:read engagement:write finding:write",
  "amr": ["pwd", "totp"],
  "jti": "tok_01J6..."
}
```

### Half 2: External tokens via pluggable OIDC

Tenants can configure one or more **OIDC providers** for federated
sign-in. Configuration lives in `iam.oidc_provider` per tenant:

| Field             | Notes                                                    |
| ----------------- | -------------------------------------------------------- |
| `issuer`          | OIDC issuer URL; metadata fetched at config time.        |
| `client_id`       | Per-tenant.                                              |
| `client_secret`   | Per-tenant; stored encrypted at rest.                    |
| `scopes`          | Defaults to `openid email profile`.                      |
| `claim_mapping`   | JSON mapping IdP claims to SentinelX role / groups.      |
| `enforced`        | If true, password sign-in is disabled for this tenant.   |
| `jit_provision`   | If true, unknown users are provisioned on first sign-in. |

On a successful OIDC callback, SentinelX validates the IdP's id_token
(RS256 with rotating keys via JWKS), maps claims to internal roles,
finds-or-provisions the user, then issues a **fresh internal JWT**
under our HS256 secret. The IdP's id_token is not propagated downstream.

This is sometimes called a "token exchange" pattern: external tokens
get short-circuited at the edge, internal tokens are used for
everything inside the platform.

### Refresh token rotation

Every refresh-token use:

1. Look up the presented refresh token by its `jti` -> row in
   `iam.refresh_token`. Verify the SHA-256 of the presented secret
   matches the stored hash.
2. If `revoked_at IS NOT NULL` or `replaced_by IS NOT NULL`, treat as
   **stolen token reuse**: revoke the entire token family, log a
   `RefreshTokenReuseDetected` audit event, force the user to re-auth.
3. Otherwise, mint a new refresh token and a new access token. Set
   `replaced_by` on the old row.
4. Old row stays in the table for 7 days to allow forensic lookup.

This is the well-known "refresh token rotation with reuse detection"
flow used by Auth0, FusionAuth, and others.

### Why no asymmetric keys (yet)

We considered RS256 / ES256 from day one and chose not to ship it yet.
The reasoning:

- We have **exactly one trust boundary** for internal tokens: the API
  layer issuing and the API layer verifying. Both live in the same
  binary. The HS256 secret never leaves the secret manager except into
  the API processes; it never travels to a customer's browser or
  agent.
- HS256 has fewer operational footguns than RS256. No `kid` header to
  pin, no JWKS to rotate, no risk of accepting a `none` alg, no
  surface for the classic `alg=HS256 with our public key` confusion
  attack (because we have no public key).
- The token verification hot path is faster with HS256.
- Customers who need RS256 because their IdP signs that way are
  **already** handled — we accept IdP id_tokens with whatever the IdP
  uses (almost always RS256 with rotating JWKS).

### Future migration to RS256

We will move to RS256 when **any** of the following happens:

- A third party (not us, not the IdP) needs to verify a SentinelX
  token. The most likely case: a customer's own backend wants to
  validate the bearer token on its own.
- We split the monolith such that the token issuer and verifier live
  in different trust domains.
- A compliance framework explicitly requires it (we have not yet been
  asked).

The migration path is:

1. Add a `key_id` claim and start issuing tokens with `kid` set, still
   HS256.
2. Stand up a JWKS endpoint, expose **the public key** of a new ES256
   key pair under a new `kid`. (We will use ES256 rather than RS256
   for smaller keys and faster verify.)
3. Issue tokens signed with ES256 for new logins; verify both HS256
   (old `kid`) and ES256 (new `kid`) for an overlap window of 24
   hours (the max access token lifetime + max refresh chain).
4. Stop issuing HS256, then stop verifying HS256.

The migration is described in detail in the operator runbook for
identity rotation.

## Consequences

### Positive

- **Minimal moving parts**. One shared secret, rotated every 90 days,
  is easier to operate than a JWKS-managed asymmetric key.
- **Fast verification**. HS256 is the fastest of the standard JWT
  algorithms; verification is roughly 0.5 us per token on commodity
  hardware.
- **Federation is decoupled from internal auth**. The "exchange IdP
  id_token for our token at the edge" pattern means the rest of the
  platform only ever sees one token shape. Adding a new IdP is a
  config change.
- **Refresh token reuse detection** is a strong control. We can
  detect a stolen refresh token within one use.

### Negative

- **Symmetric key compromise is total.** If the HS256 secret leaks,
  the attacker can mint arbitrary tokens. We mitigate with:
  - Secret manager (never on disk in plaintext).
  - 90-day rotation.
  - Audit log entry on every issuance; an off-machine forge is
    detectable when the audit log shows tokens we did not issue.
  - Short access TTL limits the window to abuse a pre-rotation
    forged token to 15 minutes.
- **Third-party verification is not possible** without giving them
  the secret, which we will not do. This is intentional and aligned
  with the threat model.
- **The IdP id_token is not validated downstream.** If we want to
  prove to a customer's downstream system that the user authenticated
  via OIDC, we have to attest separately. The `amr` claim in our
  token names the method but is not signed by the IdP.

### Risk register

| Risk                                                | Mitigation                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| HS256 secret leaks via misconfigured logging.       | Sensitive header filter in `sx-telemetry`; log scrubbing tests.  |
| Secret rotation breaks long-running sessions.       | 14-day overlap window; both old and new secret verified.         |
| OIDC `iss` confusion attack.                        | We pin `iss` per tenant; mismatch -> reject + audit alert.       |
| JIT provisioning gives admin to an unknown user.    | `jit_provision` defaults to "viewer" role only; admin needs SCIM. |
| Refresh token family revocation cascades wrongly.   | Family scoped to one device fingerprint where possible.          |

## Alternatives considered

### Alternative 1: RS256 from day one

Standard practice in many shops.

**Why not:**
- See "Why no asymmetric keys (yet)" above. Adds operational
  complexity for no real benefit at this scale.

### Alternative 2: Paseto v4 instead of JWT

Paseto (Platform-Agnostic Security Tokens) avoids most of JWT's
historical sharp edges: no alg confusion, no `none`, no kid
mishandling.

**Why not:**
- Ecosystem support is real but thinner than JWT. Most customer IdPs
  and SDKs speak JWT.
- The risks Paseto addresses (alg confusion, `none`, weak crypto) we
  already eliminate by hard-coding HS256 in the verifier — our verifier
  never reads the `alg` header at all.
- Adding a non-standard token format raises the cost of every
  customer integration.

We revisit Paseto if the OAuth WG ever blesses it as an OAuth profile.

### Alternative 3: Sessions instead of JWT

Server-side sessions in Redis or Postgres, cookie-bound.

**Why not:**
- The remote agent and the CLI need bearer tokens, not cookies.
- Sessions are great for the dashboard but force us to maintain two
  auth systems.
- JWT with a short TTL and a server-side denylist on the refresh
  token gives us most of the revocation latency benefit of sessions
  without the second system.

We do use the JWT-in-`Set-Cookie` pattern for the dashboard, but the
token itself is still a JWT for uniformity.

### Alternative 4: mTLS for service-to-service

Considered for the agent <-> platform link.

**Why not (yet):**
- The agent is a remote process in a customer network. Issuing and
  rotating client certs to customer environments has the same
  operational cost as rotating a shared secret, plus the cert plumbing.
- We use a long-lived agent token (issued at agent registration) with
  short-lived derived access tokens. The agent token is bound to a
  per-tenant scope and revocable.

mTLS is on the roadmap once we have a customer asking for it for
compliance reasons.
