## 1. Environment prerequisites surfaced

The pre-existing e2e README omits three orchestration details that must be
correct or the whole suite fails at auth:

### 1.1 `config/sentinelx.dev.yaml` out-of-date

The committed dev config file must mirror `config/sentinelx.dev.example.yaml`
byte-for-byte (or be regenerated by `scripts/dev-bootstrap.sh --force`).
On a stale `sentinelx.dev.yaml` the analyst seed (`analyst@sentinelx.dev`
/ `Analyst!Password1`) is absent and every `login(page, TEST_USER)` call
fails with backend `FORBIDDEN`.

**Fix:** `cp config/sentinelx.dev.example.yaml config/sentinelx.dev.yaml`
before spawning the monolith. This is the same seed alignment tracked as
L1-FU1 (commits `80af55f` + `04cf306`) — a QC-2026-06-25 wave green run
implicitly assumed this was already done.

### 1.2 Auth.js v5 hardcodes `localhost` — Playwright must use `localhost` not `127.0.0.1`

Regardless of `AUTH_URL` / `AUTH_TRUST_HOST` env vars, Auth.js v5 in dev
mode sets its `authjs.callback-url` cookie to `http://localhost:3000`
and redirects the credentials callback there after a successful sign-in.
If Playwright's `baseURL` is `http://127.0.0.1:3000`, the browser follows
the redirect to `localhost:3000`, the `sentinelx.session` cookie set on
`127.0.0.1` is invisible on `localhost`, the middleware rejects the
request as unauthenticated, and the whole suite fails at every
`login()` helper call.

**Fix landed 2026-07-04:** `playwright.config.ts` `baseURL` changed from
`http://127.0.0.1:3000` to `http://localhost:3000`, override with
`PLAYWRIGHT_BASE_URL` env when pointing at staging.

### 1.3 Backend `--diagnose` flag required to observe seed application

M3 dropped the default `sx-monolith` log level to `warn` (commit
`a6a96a9`), which silences the `demo data seed: applied N records` line
we grep for as a startup readiness signal. Spawn with `--diagnose` or
`RUST_LOG=info` for e2e orchestration to work reliably.

## 2. Real production bugs surfaced by QC

### 2.1 Dashboard permission gate ignores backend wildcard `*:*`

**Severity:** Medium — bootstrap-admin users are silently locked out of
every permission-gated dashboard page (IAM, SCIM, admin/secrets) and
every gated sidebar entry disappears from the nav.

**Root cause:** Backend `sx-iam` mints the bootstrap admin JWT with
`permissions: ["*:*"]` (grant-all wildcard, documented in
`crates/sx-iam/src/service/policy.rs`). Dashboard's per-page gates and
sidebar filter called `permissions.includes("<literal>")` as a plain
string check, so `["*:*"].includes("admin:users")` returned `false` and
the admin was treated as unauthorised.

**Fix landed 2026-07-04:**

- New helper `web/dashboard/src/lib/permissions.ts::hasPermission(perms, needle)` —
  wildcard-aware check honouring `"*:*"`, `"<resource>:*"`, `"*:<action>"`
  in addition to exact matches.
- Sites migrated:
  - `src/app/dashboard/iam/page.tsx`
  - `src/app/dashboard/scim/page.tsx`
  - `src/app/dashboard/admin/secrets/page.tsx`
  - `src/app/api/admin/secrets/list/route.ts`
  - `src/app/api/admin/secrets/reveal/route.ts`
  - `src/components/sidebar.tsx::visibleModules` filter
- Grep audit: zero remaining `permissions.includes` call sites outside
  `lib/permissions.ts` (self-reference in doc comment).

**Prior evidence:** The QC-2026-06-25 wave's `admin.spec.ts` targeted
the admin form on `/dashboard/iam` — it would have been failing on that
run too if the wildcard bug already existed. It's not clear when the
regression landed; likely with the sidebar 8-module refactor (commit
`715d01d`) when `requiresPermission` gating was extended into the
sidebar filter as a plain-string check.

**Follow-up:** Consider mirroring `hasPermission` semantics into the
backend `sx-iam` authoriser so a future dashboard consumer that pins
the wildcard doesn't silently regress.

### 2.2 Session callback never propagated `permissions` from JWT to `session.user`

**Severity:** Medium — companion to §2.1. Even after wildcard-aware
`hasPermission` landed, every page-level gate saw
`session.user.permissions = undefined ?? [] = []`, so `hasPermission([], "…")`
kept returning false.

**Root cause:** `web/dashboard/src/lib/auth.ts` — the credentials-provider
`authorize` callback returned a `User` with `id / email / tenantId /
sxAccessToken / sxRefreshToken / sxAccessTokenExp` but **no**
`permissions` field. The `jwt` callback propagated the sx-token fields
onto the NextAuth JWT but never lifted `permissions`. The `session`
callback promoted `id / tenantId / email / accessToken / error` but
again never touched `permissions`. Net effect: permissions round-tripped
inside the sx-api access-token payload but were invisible to the
dashboard's per-page gates.

**Fix landed 2026-07-04:**

- New helper `extractPermissionsFromJwt(token)` in
  `web/dashboard/src/lib/auth.ts` — base64-url-decodes the JWT payload,
  parses JSON, extracts the `permissions: string[]` claim
  (defensively defaults to `null` on any error).
- `authorize` callback now calls the extractor on the fresh
  access token and stashes the result on the User.
- `jwt` callback promotes `permissions` onto the NextAuth token on
  initial sign-in AND re-decodes from the refreshed access token on
  every refresh cycle (so a server-side role change surfaces without
  requiring re-sign-in).
- `session` callback lifts `token.permissions` onto
  `session.user.permissions`.
- `src/types/auth.ts` module augmentation gains a `permissions?`
  field on the JWT interface so TypeScript agrees.

### 2.3 RBA devices page: `ListUsersBody` type mismatch → server-component crash

**Severity:** Medium — the LOW-008 "Known devices" panel never
hydrated in the browser. The RSC crashed at
`result[0].value.users.map(...)`, Next.js caught the throw and
rendered the `loading.tsx` skeleton indefinitely.

**Root cause:** `src/app/dashboard/rba/devices/page.tsx` declared
`interface ListUsersBody { users: AdminUserSummary[] }` and read
`.users.map(...)`. But the backend `GET /v1/admin/users` returns the
users list **directly as the envelope's `data` field** (an array), so
`apiGet<ListUsersBody>` returned an array, `.users` was `undefined`,
`.map` threw `TypeError`.

**Fix landed 2026-07-04:**

- `type ListUsersBody = AdminUserSummary[]` (was
  `interface ListUsersBody { users: … }`).
- Reader changed to `result[0].value.map(...)` (was
  `result[0].value.users.map(...)`).
- File-level comment records the fix so a future contributor
  reintroducing the wrapper shape immediately sees the constraint.

## 4. Coverage gaps — comprehensive QC surface still uncovered

The existing suite covers the *positive path* for every dashboard route
via `qc-comprehensive.spec.ts` (positive + negative-auth on 40 routes)
+ 5 edge cases + auth + admin + engagements + findings + safety +
navigation + rba-devices + csp_nonce. What it does NOT cover:

### 4.1 Role-based negative

Every `requiresPermission`-gated route should be probed as the analyst
seed account, asserting the "You do not have <perm>" card renders and
the `/api/*` proxy returns 403 (not 401 — session is valid, only
permission is missing).

Concrete routes:
- `/dashboard/iam` — analyst-role probe
- `/dashboard/scim` — analyst-role probe
- `/dashboard/rba` — analyst-role probe
- `/dashboard/admin/secrets` — analyst-role probe
- Sidebar assertion: gated links absent from the analyst-role sidebar

### 4.2 Help / Tutorial submenu (9 new pages)

The 2026-06-25 HELP-TUTORIAL landing (commit `715d01d`) added 9 new
routes under `/dashboard/help/*`. `qc-comprehensive.spec.ts` covers
them at the positive-load level but no assertion checks that the
per-route tutorial content (Purpose / When-to-use / Workflow / Inputs
/ Role gating / FAQ / Cross-references) renders for every route the
Help index enumerates.

### 4.3 Mobile viewport / responsive

Zero specs run under a mobile viewport. The sidebar collapses into a
hamburger menu below the `md:` breakpoint (Tailwind default 768px).
That transition has no regression coverage.

### 4.4 Form validation edge cases

Specific forms with no negative-case coverage: engagement create,
finding update, tenant create, RBA weight tuning, MFA enrol, admin
create-user (partial — only invalid email is tested).

### 4.5 XSS payload input

Every free-text input in dashboard forms should reject or safely
escape `<script>` / `javascript:` / event-handler payloads. Zero
coverage today.

### 4.6 Session expiry mid-navigation

The Auth.js v5 session cookie expires after 8h. A tab left open past
expiry should redirect to /login on the next navigation. No spec.

### 4.7 CSRF / Origin spoof on write endpoints

QC-edge-cases has one CSRF assertion on `POST /v1/auth/login`. Every
other write endpoint proxied via the dashboard (`/api/admin/*`,
`/api/scim/*`, `/api/rba/*/devices`) needs the same Origin-spoof probe.

### 4.8 Keyboard-only navigation / a11y

No spec drives the dashboard via Tab / Enter / Escape only. Basic
a11y regression net absent.

### 4.9 Empty-state rendering

Every list view (findings, engagements, tenants, cloud, logs) should
render a distinct "no data" state when the backend returns an empty
list. Not asserted — the existing specs rely on seed data being
present.

### 4.10 Pagination boundaries

Findings list is paginated (backend caps at page-size 100). Spec
should exercise page 2 + last-page / off-by-one. No coverage.

### 4.11 Sort column toggling + deep-link filter

Findings + engagements support column sort. No spec.
Filter state doesn't push to URL (documented but not asserted).
